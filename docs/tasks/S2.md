# S2 — "Xem nét": animated stroke-order renderer in the character card
Status: todo · Suggested agent: Codex IDE extension, gpt-5.6-sol or gpt-5.6-terra (medium) — ask first, per pm-session's model table (Android timing/animation is new ground in this codebase) · Session: new · Size: M · Device check: user

## Why
S1 ships the stroke-pack data (`{char: {strokes: [SVG path "d" string per stroke], medians:
[[x,y]...] per stroke}}`) and downloads it once. This task renders it: the character card gets
a "Xem nét" (view strokes) action that plays the character's strokes in order, view-only — no
tracing, no scoring (decided in architecture/characters.md). Confirmed in S1's research: every
path only uses `M L Q C Z` (no arcs), so a small hand-written parser is enough — no need for a
reflection hack on the hidden `android.util.PathParser`.

## Do
1. **SVG path parser** (new file, e.g. `ui/characters/StrokePath.kt`, ≤ 100 lines): parse a
   Hanzi Writer `d` string (`M`, `L`, `Q`, `C`, `Z`, all absolute, space-separated numbers) into
   an `android.graphics.Path` / Compose `Path`. Hanzi Writer's paths are authored on a 1024×1024
   viewBox — scale to the composable's actual draw size (square, `size.minDimension`), flip Y if
   the sample renders upside down (check against a known character's expected shape visually —
   one device check covers this, see Acceptance).
2. **Animated renderer** (`StrokeAnimation.kt` or similar, ≤ 150 lines): given a `StrokeEntry`,
   draw each stroke's path progressively using `PathMeasure` segment-trim (`getSegment(0f,
   length * progress, destination, true)`), one stroke after another, each driven by an
   `Animatable<Float>` (e.g. ~400–600ms per stroke, already-drawn strokes stay solid). Expose
   play / pause / replay-from-start. No trace/tap scoring — this is playback only.
3. **"Xem nét" entry point:** add the action to `CharacterCard.kt` (button or icon, visible only
   when the character's stroke data is available in the loaded `StrokePack` — i.e. present in
   the downloaded map, not just `stroke_available` from the lesson's `characters.json`, since
   the base pack could be mid-download or stale); tapping opens the animation (inline in the
   card or a nested sheet, your call — keep `CharacterCard.kt` under 300 lines, split the
   animation view into its own file regardless).
4. **ViewModel plumbing:** wherever `CharacterIndex` is currently loaded (the screen/ViewModel
   that owns the character card), also load the `StrokePack` once via
   `CourseRepository.strokePackFile()` (from S1) and pass the relevant `StrokeEntry?` down —
   stateless rendering, same pattern as the rest of the character feature.
5. **Tests:** a Compose UI test asserting the "Xem nét" button is absent when the char has no
   stroke data and present when it does (fake a small `StrokePack` fixture, don't need the real
   9575-char set); a unit test for the path parser against 2–3 real sample "d" strings from
   `data/hanzi_writer/` asserting the resulting `Path`'s bounds are non-degenerate (non-zero
   width/height) — don't assert exact pixel output.
6. Update `docs/STATUS.md` (S2 done) and add a `docs/token_log.md` row. Do not commit.

## Acceptance
- A character with stroke data shows "Xem nét"; tapping it animates strokes in order and ends
  with the full character visible; replay restarts from stroke 1.
- A character without stroke data (or while the base pack hasn't downloaded yet) shows no
  "Xem nét" button and does not crash.
- The rendered shape is recognizably the character on a real device for at least 3 different
  characters of varying stroke count (device check, since this is the part a unit test can't
  cover — wrong Y-flip or wrong scale is a visual bug, not a logic bug).
- `bash scripts/check.sh` passes; no new file over 300 lines in `docs/CODEMAP.md`.

## Device check (user, ≤ 8 steps)
1. `just app`, open a lesson with character data, open a character's card.
2. Tap "Xem nét" → strokes draw one at a time in the right order, ending with the full character.
3. Tap replay → animation restarts from stroke 1.
4. Open a character/component with no stroke data → confirm no "Xem nét" button, no crash.
5. Repeat steps 1–2 for 2 more characters with different stroke counts (e.g. a 2-stroke and a
   10+-stroke character) — shape should look right, not mirrored/flipped/squished.
